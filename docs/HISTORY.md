# JPX 日次历史获取与限制

`GET /api/margin?code=7974&days=20` 最多返回 20 个有有效股票记录的公表日，
不是 20 个自然日。响应字段不变；`count` 为实际数量，`rows` 按日期升序。
HTTP 200 或 `ok:true` 不代表已满足请求数量，应同时检查 `count` 和 `upstream`。

## 官方路径核实

2026-10-08 检查 JPX 官方 `https://www.jpx.co.jp/markets/statistics-equities/margin/01.html`：
索引只有 2026-10-01、02、05、06、07 五个日期。旧实现的 `gather()` 只遍历
该页链接，调整 `days` 不会增加候选日期，因而最多返回五条。
实测索引中 `tvdivq0000001rnl-att/20261007_mtall.pdf` GET 返回 200，内容以
`%PDF-` 开始；同目录 `20260930_mtall.pdf` GET 返回 404。
9 月 29、28 日候选 GET 也返回 404；重复 9 月 30 日请求由缺失缓存处理，
实测网络调用数为零。9 月 25、23 日候选 HEAD 返回 404。未发现可保证获取全部日次历史的
官方公开归档，不把其他统计表或旧周次数据当作日次序列。

## 新流程

1. 读取当前官方索引，并合并本地完整日次 PDF 缓存，统一按日期倒序处理。
2. 不足时，仅使用当前索引实际出现的官方 PDF 目录生成日期候选；逐个 GET，
   完整性验证成功后才解析、计数。路径候选并不表示 JPX 提供了该文件。
3. 跳过周末；日本节假日和不存在文件以官方实际响应为准，404/410 记入
   磁盘缺失缓存，6 小时后允许重试。新索引链接也不会永久被旧的 404 阻挡。
4. 候选不晚于索引最新公表日，最多向前 90 自然日，且不早于日次全銘柄系列
   起点 2026-09-28；不探测当天尚未公表的数据，不混入旧周次文件。
5. 最多返回 `days` 个有效记录（API 上限仍为 40）；不足时返回实际数量，
   不补零、不插值、不伪造日期。索引失败时保留现有 stale 语义，并尝试已有缓存。

## QNAP 资源与请求预算

- 全局一次网络传输、一次 PDF 解析，历史收集串行；不创建并行 PDF 解析池。
- 网络请求之间至少间隔 1 秒；单次 socket 超时 20 秒，瞬时错误最多重试一次。
  404/410 不重试；瞬时错误耗尽后暂停网络请求 60 秒。
- 单次下载最多 64 MiB；PDF 及 JSON 原子写入、版本/源指纹检查和 generation
  保护保留，完整 PDF 和有效解析结果不重复下载/解析。
- 每次历史补全的未知日期探测使用 45 秒软网络预算；正在执行的请求及一次
  重试可以越过预算。此预算不含已索引文件的获取、解析及等待锁的时间，不能
  当作整条 API 的响应时限。预算用尽仍可读取已有完整 PDF。
- 普通进程结果缓存 10 分钟后过期；`fresh=1` 仍复用同轮索引和未变化的解析
  缓存。PDF、JSON 及缺失缓存随 `/app/.cache` 保留，部署挂载路径不变。

首次查询 20 个 PDF 的解析在 Celeron 上可能很慢；未进行 NAS 实机性能测量。
随后相同股票/日期命中缓存，显著减少网络与解析开销。历史补全依赖 JPX 当前
实际保留文件和此前本地积累；如果官方删除了文件且 NAS 没有缓存，就无法
保证补齐 20 天。缓存不会自动从别的 NAS 或第三方来源恢复。

## 验证

`python -m unittest -v test_history.py` 为离线模拟，覆盖有效交易日计数、周末、
节假日/缺失、404 负缓存与过期、超时重试/冷却、完整 PDF 缓存、索引轮转、
预算、内存缓存过期、健康 API 和实际数量响应。现有 JS、Python 及发布测试
继续运行；CI 不依赖 JPX 实时网络。GHCR 发布流程及 QNAP 部署配置未改动。
